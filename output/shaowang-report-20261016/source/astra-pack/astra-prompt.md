## 6. 写作要求（最重要）

### 6.1 核心原则
1. **言之有物**：每一段都要有具体信息——一个机制、一个参数、一个取舍、一个例子或一个证据。删掉任何去掉后不影响理解的句子。
2. **把亮点写出来**：亮点不是形容词，而是“别人怎么做 → 我们怎么做 → 差别带来什么”。例如“边带理由”这件事，要写出它解决了什么（幻觉边无法追溯）、怎么保证（写进 Schema 必填）、用户看到什么（点击边弹出理由）。
3. **自然流畅，像人写的**：句子长短交错，段落之间有承接（“这样做的代价是……”“这引出了另一个问题……”）。允许适度的判断和体会，但必须有依据。
4. **逻辑连贯**：每章开头说本章回答什么问题；每节先讲问题再讲方案；前文提出的挑战在后文有呼应，第五章创新点能在第二、三章找到对应设计，在第四章找到对应评测。
5. **切忌写成**：代码注释（“该函数用于……，参数为……，返回……”）、接口文档（成段罗列字段名）、单纯实验报告（“实验目的／实验步骤／实验结果／实验结论”模板）、宣传稿（堆形容词）。字段名、参数只在必要处点到，详细字段留给表格。

### 6.2 正反例

**例 1：讲设计决策**
- ✗ 反例：“系统采用 RRF 算法对检索结果进行融合，有效提升了检索效果。”
- ✓ 正例：“三路检索器的打分没有可比性：BM25 分数没有上界，向量相似度落在 0 到 1 之间，图扩展的结果干脆没有分数。与其为加权求和反复调参，不如只看排名——RRF 把每条结果在各路中的名次换算成分数再相加，同时出现在多路结果中的证据自然排在前面。”

**例 2：讲亮点**
- ✗ 反例：“本系统创新性地实现了可解释的知识图谱，具有重要的理论意义和应用价值。”
- ✓ 正例：“让大模型补关联并不难，难的是事后说得清每条边从哪里来。哨望把理由、置信度、生成方法和创建者写成关系边的必填字段，缺一项就过不了 Schema 校验；分析师在图谱里点开任意一条边，看到的是‘GHSA 的 aliases 字段包含该 CVE 编号’这样可以当场核对的句子。”

**例 3：讲代码**
- ✗ 反例：“resolve_field 函数接收 field 和 cands 两个参数，首先判断 field 是否在 SPECIAL_RULES 中，然后对 cands 排序，最后返回 Resolution 对象。”
- ✓ 正例：“裁决顺序被写成一个三元组排序键，而不是三层嵌套的 if：等级、置信度、更新时间依次比较，前一级分出胜负就停止，这正是设计规则本身的语义，评审读代码时不必在分支里推演。”

**例 4：讲待测**
- ✗ 反例：“经测试，系统端到端时延 P95 约为 2 小时，远低于 6 小时要求。”（没有实测，属于编造）
- ✓ 正例：“采集时延的上限基本由轮询间隔决定，P0 来源应稳定在分钟级；真正的不确定性在处理阶段，尤其是大模型调用和暴露面查询的排队。实测值为【待测：漏洞类情报端到端时延 P95，目标值 ≤6 h】。”

**例 5：讲实测**
- ✗ 反例：“经过大量测试，我们对测绘语法进行了优化，效果良好。”
- ✓ 正例：“第一次用 app:"Ollama" 查询，Quake 返回约 82 万条，比 Cisco Talos 用 Shodan 数出的 1139 个高出近三个数量级。我们据此判定语法过宽，改为‘默认端口 11434 且响应含 Ollama is running’，全球计数降到约 17.2 万；再抽 50 条只看元数据，44 条吻合，精确率 88%，过了 80% 的上线门槛。”

### 6.3 禁用套话清单
不得出现以下表达（或同义改写）：
- 开头套话：随着……的快速发展／日益普及／近年来，……越来越受到关注
- 空洞评价：具有重要意义、具有重要的理论意义和应用价值、意义重大、填补空白、国内领先、业界首创、首个、革命性
- 无数据的程度词：显著提升、极大地提高、大幅降低、有效解决、全面提升、性能优异、效果良好
- 营销词：赋能、助力、打造、一站式、全方位、多维度、深度融合、全链路（作为空泛形容时）、智慧化
- 填充连接：值得注意的是、不难发现、众所周知、总而言之、综上所述（结论段可用“总结来看”一次）、由此可见（无推导时）
- 机械结构：每段都“首先……其次……最后……”；每节都以“本节将介绍”开头
- 自我指代滥用：每段都以“本系统”“本文”开头（换成“哨望”或直接写主语）
- 形式问题：表情符号、感叹号、整段加粗、口语化“咱们”“搞定”、中英文括号混用
