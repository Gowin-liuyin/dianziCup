# 第四章 测试与分析

当前能够报告的实测是来源入口连通性和 Quake 的 Ollama 计数校准。监测时效、富化准确率、问答质量、故障自愈与编码智能体兼容性尚待测量。本章先冻结样本、指标和对照方式，再保留结果位置；只有这样，后续回填的数字才能回答设计是否成立，而不是仅仅展示一个看起来不错的总分。

## 4.2 监测时效测试
### 4.2.1 测试方法

五段时间戳把发现与处理分开。端到端时延以 queryable_at 减 source_published_at，采集时延以 first_seen_at 减 source_published_at，处理时延以 queryable_at 减 first_seen_at。单次 HTTP 耗时只覆盖一个请求，不能替代任何一个完整阶段的时延。

{{F-27}}

统计对象限定为漏洞类首次发现，来源为 NVD、GHSA、OSV、厂商公告和 huntr。DEMO 排除，日更来源单列。仅精确到日的发布时间按当天零点计算，可能保守高估时延；记录中保留时间精度，使不同来源的分位数能被正确解释。

连续观测目标不少于七天，实际不足时如实报告天数。重试、降级和配额等待都属于系统实际运行条件，不能只挑选顺利处理的样本。来源更新时间与首次发布时间分开保存，防止一条旧漏洞补评分时被当作新发布样本。

## 4.3 富化与关联准确率测试
### 4.3.1 金标集构建

计划使用二百条金标，覆盖多源合并、ATLAS 映射与版本区间三类判断。样本加入无 CVE 公告、双 CVE 别名、CVSS 分歧和不规范版本号，避免只测容易的规则直连关系。两人独立标注，分歧由第三人仲裁；一致性为{{PH:37}}。

标注不仅给结论，还要保留支撑材料，尤其说明候选为何不能合并、某版本为何位于边界。否则模型输出与参考答案一致时，仍无法判断它是否依据正确证据。金标集当前是评测计划，不能把二百这一规模写成已经完成标注的数量。

### 4.3.2 评测协议与结果

多源合并用精确率与召回率，版本判断看区间一致率，ATLAS 看 Top-1 准确率。三类任务的错误含义不同，所以先按类型给出混淆结果，再报告总体，不用大量容易的规则样本掩盖弱关联误差。

## 4.4 问答质量测试
### 4.4.1 评测集与基线

约一百题覆盖单文档事实、跨文档检索、多跳推理和深度分析，每题给出参考答案与支撑证据。事实题检查编号、评分与版本，多跳题检查组件、时间、公开链接和技术映射的组合约束。题型分开统计，才能知道图扩展帮助的是哪类问题。

三组配置为向量检索 RAG、BM25 与向量融合、三路检索加 Critic。模型和生成提示保持相同，只改变检索与校验。第三组同时引入图扩展和 Critic，因此整体差异首先说明组合方案效果；若要分别归因，还应结合已有的 Critic 前后分析，不能从三组总分直接推出每个组件的独立贡献。

### 4.4.2 评价指标与结果

答案准确率由人工对照参考答案判断；引用正确率看引用是否支持所在句，引用覆盖率看结论句是否有证据支撑。RAGAS 忠实度作为辅助指标，不能替代人工对版本边界与风险结论的判定。[33]

{{T-12}}

目前表中未填任何质量结果，也没有把模板回答计为多跳推理。回填时应同时查看错误答案是否带有看似正确的引用、partial 是否清楚标注、资料缺失时是否承认不知道。多跳命中数增加并不必然提高答案质量，新增证据是否相关需要通过这些指标检验。

## 4.5 编排可靠性与故障注入测试

可靠性测试关注故障之后的任务和事实是否恢复，而不是只看进程能否重新启动。六类场景覆盖限流、短时服务端错误、连续周期故障、参数错误、单维超时和 worker 终止，分别对应等待、死信、熔断、拒绝重试、隔离与检查点恢复。

{{T-13}}

每次注入要记录触发、发现、降级、故障消除和恢复的时间，并确认没有丢失任务或重复形成事实。自愈成功率按故障消除后在设定时间内恢复且无数据丢失的场景计算，平均恢复时间从故障消除算起。结果为{{PH:62}}，恢复时限仍需在运行协议中冻结。

参数错误是一个容易混淆的场景。400 不应被反复重试，进入死信并告警才是预期行为；该场景不能因为没有自动重放成功就被误判为系统失败，也不能因告警出现就宣称业务数据已经恢复。每个场景应按各自可观察行为验收。
